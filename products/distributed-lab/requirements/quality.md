# 一致性、活性與變更品質

基準、可知序列及固定時間窗口均引用 [scenarios.yaml](../data/scenarios.yaml)；模型與證據回報依[共同評測](../../../docs/model-challenge-evaluation.md)。

### REQ-QLT-01 以可知小型歷史校準判定且保留未判定狀態

判定者必須辨認具有明確合法序列或違反原因的小型歷史。任意歷史若未分析完成、逾時或資源耗盡，只能標為未判定；不能把沒有找到反例當作線性一致性通過。

- 里程碑：M1
- 優先：必要

#### AC-QLT-01 合法、非法與未判定互不混用

- Given `small_histories` 全部可知案例及 `analysis_outcomes` 的未完成情境
- When 對各歷史執行獨立於展示畫面的結果判定
- Then 已完成結果符合各案例期望與見證；未完成情境一律顯示未判定並保留原因，不被納入通過案例，也不假造完整檢查證據
- 驗證：自動

### REQ-QLT-02 穩定且公平的多數窗口內完成操作

當存活多數互相可靠送達、客戶端可達且公平執行持續時，既有待定及新送的合法操作須在資料窗口內完成。不滿足此前提時不要求所有請求完成，但安全規則與真實狀態回報仍有效。

- 里程碑：M2
- 優先：必要

#### AC-QLT-02 恢復穩定多數後在固定窗口內完成

- Given `liveness_case` 的故障前綴及隨後持續成立的穩定條件
- When 公平推進至資料指定截止時間
- Then 待定寫入及後續新讀取均得到資料要求的結果，完成時刻未超出窗口；執行中不得偷偷延長期限或略過待定操作
- 驗證：自動

#### AC-QLT-03 缺少活性前提不產生虛假成功

- Given `no_liveness_case` 的少數存活與無法送達條件
- When 持續推進至資料中的觀察終點並嘗試新寫入
- Then 結果維持資料允許的未確認或不可用狀態，且日誌說明缺少的前提；不以未完成本身判為活性違反，也不以成功回覆掩蓋不可用
- 驗證：自動

### REQ-QLT-03 壓縮變更前後業務結果等價

快照及壓縮可以改變事件細節與本地儲存量，但不能改變相同順序操作的業務結果、請求身分或已確認值。第二輪需同時保留原故障情境及快照恢復的證據。

- 里程碑：M3
- 優先：必要

#### AC-QLT-04 快照配對情境與既有案例均維持承諾

- Given `snapshot_equivalence` 的開啟／關閉壓縮配對及 `regression_cases`
- When 以各情境既定順序完成實驗及恢復
- Then 配對中的成功結果、讀值及邏輯請求身分一致，允許壓縮事件細節不同；所有既有案例仍符合其期望，未執行項如實列為未驗證
- 驗證：自動

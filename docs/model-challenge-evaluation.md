# 高難度模型挑戰：共同評測規格

狀態：draft。這是七個候選產品共用的業務評測條件，不是模型排名、實測報告或產品實作授權。各產品的 PRD、SDD、REQ／AC、業務資料與里程碑是該題的需求來源；本頁定義如何公平比較交付結果。

## 1. 目的與選題

比較模型在有限內容、相互制約的規則與可觀察結果之下，能否完成端到端流程、維持正確性、處理變更，並提供可追查的證據。採用七個互相獨立的題目，不要求單次把全部產品做完。

| 產品 | 主要能力 | 第一輪完整流程 | 第二輪變更 |
| --- | --- | --- | --- |
| [MMO 經濟危機實驗室](../products/mmo-economy/README.md) | 建模、帳務、因果追查 | 採集、製造、交易、消耗、查帳 | 物品腐敗與持有中的交易 |
| [太空船打撈](../products/space-salvage/README.md) | 空間、物理、視覺整合 | 進入、拆卸、回收、撤離 | 循環供電與繞路 |
| [魔法編譯器](../products/spellcraft/README.md) | 規則組合與除錯體驗 | 編輯、檢查、施放、逐步解釋 | 新增油的交互作用 |
| [工廠韌性](../products/factory-resilience/README.md) | 資源約束、排程、最佳化 | 原料、加工、搬運、組裝、交付 | 加工中故障與回收 |
| [可解推理案件](../products/solvable-mystery/README.md) | 約束推理、生成一致性 | 產生案件、取得線索、推理、解答 | 共謀掩護 |
| [分散式故障實驗室](../products/distributed-lab/README.md) | 一致性、故障、恢復 | 讀寫、故障、恢復、歷史檢查 | 日誌壓縮與落後節點恢復 |
| [軌道任務實驗室](../products/orbital-lab/README.md) | 數值推理、物理、預測 | 規劃、推進、預測、完成任務 | 高速穿越與碰撞事件 |

建議先做 mmo-economy，再做 space-salvage；想同時評估遊戲與抽象規則可先選 spellcraft。這是選題建議，不是預先判定任一模型的優劣。

## 2. 授權、版本與評測單位

- 每次評測單位為「一個產品 × 一個已選里程碑範圍 × 一份鎖定規格版本 × 一套執行條件」。各產品 M1／M2／M3 以自己的 milestones.md 為準。
- 本次交付只有 draft 文件；`draft` 收錄不代表同意實作，Draft PR 不代表已合併或已批准。
- 正式評測前，owner 選題並批准涉及的需求、業務資料及本頁評測條件。參考案例的預期結果先以可信參考或獨立計算驗證，指令、版本、輸出留在批准 PR；未驗證不得宣稱 AC 已鎖定。
- 實作依據以 specs commit SHA 識別。評測開始後不追改同一場次的驗收門檻；改動另開規格版本並保留舊結果。
- 若工具、Agent 工作流程、外部模型協助或環境不同，結果名稱必須包含整套配置。不得把整套開發系統的結果歸因為基礎模型單獨能力。

## 3. 評測前必填條件

這些是結果可比的必要資訊，不指定實作框架或測試程式位置。

| 條件 | 必須記錄的內容 | 缺漏時處理 |
| --- | --- | --- |
| 需求基準 | 產品、里程碑、規格 SHA、資料版本、公開案例集合 | 不開始正式評測 |
| 模型配置 | 可核實的模型識別、推理設定、上下文與工具配置；無法查得填 unknown | 僅能做有限配置比較 |
| 起始材料 | 同一份提示、同一基準版本、同一素材包及授權 | 條件不同分組報告 |
| 外部協助 | 是否允許網路、文件檢索、現成程式庫、其他模型、人工修補 | 先鎖定再執行 |
| 主預算 | 等實際費用或等牆鐘時間擇一，寫明數值、含哪些活動及停止條件 | 不設定臨時有利於某模型的上限 |
| 修復額度 | 首次交付後允許的修復輪數與總預算，所有參與者一致 | 首次與修復後分開記錄 |
| 執行設備 | CPU、GPU、記憶體、作業系統、瀏覽器版本、畫質、解析度與縮放、供電模式 | 不比較效能結果 |
| 載入條件 | 冷／暖快取、網路條件、素材是否已下載、量測起訖 | 不比較載入時間 |
| 裁判 | 獨立判定來源、人工審閱規則、案例保管者 | 無獨立依據不得算已證明正確 |

時間、金額、效能上限由選定場次事前填妥並固定。各產品 data 中的候選門檻屬提案，沒有指定設備及參考結果時不得宣稱已實測可達。沒有真實計量的 token／費用填 unknown，不能以工具呼叫次數換算假裝實耗。

## 4. 三輪交付

### 第一輪：完整切片

從相同基準開始，完成各產品 M1 的完整使用流程。記錄首次可重現啟動、首次完整流程、首次必要 AC 全部通過的時間；未達成就記未達成，不以首頁截圖替代。

### 第二輪：品質與變更

在第一輪候選成果上，依本次選定範圍驗證 M2 品質，再提供相同的 M3 變更包。產品文件已公開 M3 大方向，因此它不是秘密題；比較的是變更成本與舊行為保持程度。若要評估意外需求，另建未公開但等價、已批准的變更包，不把本 repo 的公開例子稱為保留題。

第三方素材、手工修復、模型呼叫和重試仍計入原定範圍。不可把整個作品偷偷換成預先完成的參考實作，再報告為增量變更成功。

### 第三輪：保留案例

保留案例只能改變規格已允許的輸入、事件順序、亂數種子或邊界值，不能臨時加入未公布的產品義務。公開 data 是示例與基準，不是保留案例。

保管者在評測前封存案例版本及內容摘要，參與模型不能讀取；結果公布後保留足夠重現證據。若無法保持隔離，標為公開案例測試。保留案例失敗時記下原始輸入與失敗，修復後另記新結果。

## 5. 通過條件與分數

先判斷資格，再列各維度表現。任何必要 AC 失敗、未跑、裁判無法得出結論或缺證據，該里程碑都不能標為通過；漂亮畫面或高效能不能抵消必要規則失敗。

| 維度 | 建議權重 | 可比證據 |
| --- | --- | --- |
| 行為正確 | 35 | 規則、不變量、拒絕非法操作、獨立裁判與 AC 覆蓋 |
| 完整流程 | 20 | 從啟動到任務結束的操作紀錄與結果 |
| 視覺與操作 | 15 | 固定任務的資訊可讀性、操作回饋、完成度及使用者觀察 |
| 效能與穩定 | 10 | 指定設備完整場景的量測，失敗與異常一併列出 |
| 變更後品質 | 20 | 新需求通過、原 AC 回歸、存檔相容或明確拒絕、修復投入 |

權重是建議產品決策，正式場次開始前固定；各維度先報原始結果，總分只是輔助。人工評分採共同的 0–4 級：0 無法完成；1 靠大量提示或修復才完成；2 可完成但有明確障礙；3 自行完成且資訊完整；4 完整且能清楚解釋錯誤與恢復。評語必須指出實際任務與證據；人工評審盲化模型名稱可行時採用。

自動項以預先公布的 AC／量測映射計分，不直接套人工感受。N/A 不當滿分；只比較適用維度相同的結果。相同題目至少使用事先固定的多組種子或輸入，報告分布與失敗案例，不挑最好一次代表全部。

## 6. 最低證據

每次交付提供：

1. 真實產物 commit SHA、PR、規格 SHA、使用的素材與資料版本。
2. 乾淨環境的啟動方式、實際執行環境與端到端操作結果。
3. 逐條 AC 的 pass／fail／not-run／inconclusive，以及對應指令、輸出、紀錄或人工確認者。
4. 可重播輸入、關鍵世界狀態或帳務／歷史摘要；像素完全一致不是所有題目的必要條件。
5. 效能量測的場景、暖機、期間、分位數與原始資料；不得只量空場景或省略失敗區段。
6. 第一次交付與修復後的個別結果、人工介入次數及內容、實際可知投入與未知值。
7. 失敗、未驗證項目及唯一恢復入口。

文件結構檢查只證明文件符合 repo 規範。參考算例檢查只證明該案例的預期值。產品驗收必須由實作產物實際執行取得，三者分開報告。

## 7. 公開與成本邊界

- 七題使用虛構人物、商品及合成資料。公開資料不包含私人對話、登入資訊或公司內容。
- 本地單人流程為首版共同邊界；需要伺服器的題目可在單機執行。帳號、多租戶、付費營運及公開部署另議。
- 產品可以使用授權明確的素材與程式庫；正式比較前固定可用清單，避免把不同素材條件當成模型差異。
- 比較不需要每個模擬角色呼叫線上 LLM。若新增執行期模型依賴，先變更成本與可重現性規格。
- 發布、部署、建立付費資源與產品實作，均不包含在本次文件草案交付中。

## 8. 參考資料與判讀限制

以下是前期選題背景，不規定產品的技術架構；具體選型留到實作 repo：

- [SimPy 官方說明](https://simpy.readthedocs.io/en/stable/index.html)：離散事件與有限資源的建模背景。
- [Mesa 官方說明](https://mesa.readthedocs.io/stable/overview.html)：代理行為模擬背景。
- [Three.js WebGPURenderer](https://threejs.org/manual/pages/webgpurenderer)：圖形能力與目前支援範圍；不能從範例推定本產品效能。
- [Rapier determinism](https://rapier.rs/docs/user_guides/javascript/determinism/)：相同引擎版本、初始化及事件條件的重要性；不能直接保證整個遊戲完全可重現。
- [OR-Tools job-shop](https://developers.google.com/optimization/scheduling/job_shop)：排程約束與小型參考案例背景；只有明確證明最優的結果可當最優解。
